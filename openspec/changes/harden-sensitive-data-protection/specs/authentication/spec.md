## ADDED Requirements

### Requirement: 利用を許可するアカウントの限定
API サーバは、運用者が設定した許可リストに含まれる認証サービスの識別子を持つ要求だけを、認可が必要な経路で受け付けなければならない (SHALL)。署名・発行者・オーディエンス・有効期限が正当なトークンであっても、識別子が許可リストに無ければ拒否しなければならない (MUST)。許可リストが空または未設定のときは、認可が必要な経路の要求をすべて拒否しなければならない (MUST)。この判定は、認証サービス側の新規登録の可否の設定に依存してはならない (MUST NOT)。

拒否の応答は、認可情報の欠落・失効（401）と区別できる状態と識別コードで返さなければならない (SHALL)。拒否した要求について、アプリ側のユーザーを作成してはならない (MUST NOT)。

クライアントは、この拒否を受け取ったら保持しているトークンを破棄し、サインイン画面に、このアカウントでは利用が許可されていない旨を示さなければならない (SHALL)。拒否を受けた後に、同じトークンで要求を繰り返してはならない (MUST NOT)。

#### Scenario: 許可されたアカウントで要求する
- **WHEN** 許可リストに含まれる識別子を持つ、正当なトークンで API を呼び出す
- **THEN** システムは要求を受け付け、通常どおり応答する

#### Scenario: 許可されていないアカウントで要求する
- **WHEN** 許可リストに含まれない識別子を持つ、正当なトークンで API を呼び出す
- **THEN** システムは 401 とは異なる状態と、許可されていないことを示す識別コードで要求を拒否し、チャネル・ポスト・添付のいずれも返さない

#### Scenario: 許可されていないアカウントのユーザーを作らない
- **WHEN** 許可リストに含まれない識別子を持つトークンで、初めて API を呼び出す
- **THEN** システムはアプリ側のユーザーを作成しない

#### Scenario: 許可リストが未設定
- **WHEN** 許可リストが空または未設定の状態で、正当なトークンによる要求が到達する
- **THEN** システムは要求を拒否し、どのアカウントにもデータを返さない

#### Scenario: 認証サービスの新規登録が誤って有効になる
- **WHEN** 認証サービスで新規登録が有効になり、招待していないアカウントがサインインして API を呼び出す
- **THEN** システムは当該アカウントの要求を拒否する

#### Scenario: 認可を要さない経路
- **WHEN** ヘルスチェック、または定期実行用の内部経路へ要求が到達する
- **THEN** システムは許可リストの判定を行わず、それぞれの既存の規則で処理する

#### Scenario: クライアントが拒否を受け取る
- **WHEN** サインイン直後のクライアントが、許可されていないことを示す拒否を受け取る
- **THEN** システムは保持しているトークンを破棄してサインイン画面へ戻り、このアカウントでは利用が許可されていない旨を表示する

## MODIFIED Requirements

### Requirement: ユーザーの登録
システムは、許可リストに含まれるアカウントの初回サインイン時に、認証サービス上の識別子と対応するユーザーをアプリ側に登録しなければならない (SHALL)。許可リストに含まれないアカウントを登録してはならない (MUST NOT)。アプリ側のユーザーレコードは、特定の認証サービスに依存しない形で識別子を保持しなければならない (SHALL)。

#### Scenario: 初回サインイン
- **WHEN** 許可リストに含まれ、これまでにアプリを利用したことのないアカウントが初めてサインインする
- **THEN** システムは認証サービスの識別子に対応するユーザーを作成し、以後の投稿の作成者として関連付ける

#### Scenario: 2 回目以降のサインイン
- **WHEN** 既に登録済みのアカウントがサインインする
- **THEN** システムは既存のユーザーを再利用し、重複したユーザーを作成しない

#### Scenario: 登録済みのアカウントが許可リストから外れる
- **WHEN** アプリ側にユーザーが登録済みのアカウントが、許可リストから外された後に API を呼び出す
- **THEN** システムは要求を拒否し、登録済みのユーザーが存在することを理由に受け付けない

### Requirement: トークンの安全な保管
システムは、認証トークンをプラットフォームごとの保管領域に格納しなければならない (SHALL)。Electron は OS の安全な資格情報保管領域を用いなければならない (SHALL)。Electron で安全な資格情報保管領域が利用できない場合、トークンはプロセスのメモリにだけ保持し、ディスクへ書き出してはならない (MUST NOT)。iOS ネイティブアプリは Keychain を用いなければならない (SHALL)。ブラウザ（PWA）は、再訪時にサインイン状態を復元できるよう、リフレッシュトークンを当該 origin の永続 web ストレージへ保存しなければならない (SHALL)。アクセストークンはメモリ、またはリフレッシュトークンと同じ永続レコードのいずれかに保持しなければならない (SHALL)。トークンを第三者 origin やクエリ文字列へ書き出してはならない (MUST NOT)。

#### Scenario: デスクトップでの保管
- **WHEN** Electron アプリがトークンを保持する
- **THEN** システムは OS の安全な資格情報保管領域を用いて保存する

#### Scenario: デスクトップで安全な保管領域が使えない
- **WHEN** OS の安全な資格情報保管領域が利用できない状態で、Electron アプリがトークンを保持する
- **THEN** システムはトークンをメモリにだけ保持してディスクへ書き出さず、アプリの終了後に再起動するとサインインを求める

#### Scenario: 過去に暗号化せずに保存したトークンが残っている
- **WHEN** 暗号化されていないトークンの保存ファイルが残った状態で、Electron アプリが起動する
- **THEN** システムは当該ファイルの内容をトークンとして読み込まず、ファイルを削除する

#### Scenario: ブラウザでの保管と復元
- **WHEN** PWA またはブラウザがトークンを保持する
- **THEN** システムはリフレッシュトークンを当該 origin の永続 web ストレージへ保存する

#### Scenario: ブラウザを閉じたあと再訪する
- **WHEN** サインイン済みのブラウザまたはホーム画面 PWA を終了し、同じ origin で再度開く
- **THEN** システムは保存したリフレッシュトークンからセッションを復元し、直ちにサインイン画面へ戻さない

#### Scenario: ブラウザでサインアウトする
- **WHEN** ブラウザまたは PWA でユーザーがサインアウトする
- **THEN** システムは永続 web ストレージ上のトークンを削除する

#### Scenario: iOS での保管
- **WHEN** iOS アプリがトークンを保持する
- **THEN** システムは Keychain を用いて保存する
