## Why

`harden-sensitive-data-protection` で、次の 4 点を閉じた。
- 誰が読めるか（許可リスト）
- 消したものが消えるか
- バックアップを誰が開けるか
- XSS の被害範囲

それでも本文は、API・Supabase・バックアップの中で平文として存在する。`DATABASE_URL` の漏えい、Vercel や Supabase 側の侵害、運営者の誤操作のどれか 1 つで、秘匿性の高いメモが読める。

秘匿性の高いメモに限って、サーバー側のどこにも平文と鍵を置かない場所が要る。一方で、そのメモは次のいずれの端末からも読めなければならない。
- 個人用 Mac（Electron）
- 個人用 iPhone（PWA）
- 会社支給 Mac（ブラウザ）

全文検索は、このようなメモについては不要である。

秘匿するかどうかはポストごとではなく、チャネルで決める。メモの置き場所を選ぶだけで扱いが決まるので、暗号化を付け忘れた平文が秘匿用の場所に混ざることが無い。

## What Changes

- **暗号化チャネル**: チャネルを作るときに、暗号化チャネルにするかを選べるようにする。既定は非暗号化チャネルとする。
  - 暗号化の有無は作成後に変えられない。リネーム・並べ替え・親の付け替えでも変わらない。
  - 暗号化の有無は親子関係と関係なく、チャネルごとに決まる。
  - チャネル一覧とチャネルの見出しに、暗号化チャネルの印を付ける。
- **投稿の暗号化**: 暗号化チャネルに投稿するポストと、そのスレッドへの返信は、すべてクライアントで暗号化してから送信する。サーバーは暗号文だけを保存する。
  - 非暗号化チャネルは従来どおり平文で扱い、ポストごとの暗号化の選択は設けない。
  - サーバーは、暗号化チャネルへの平文の投稿と、非暗号化チャネルへの暗号文の投稿を拒否する。
- **端末をまたぐ鍵**: ワークスペースに 1 つのデータ鍵を作り、パスフレーズと復旧キーから導いた鍵でそれぞれ包む。包んだ状態のデータ鍵をサーバーに置く。
  - どの端末でも、同じパスフレーズを入力すれば解錠でき、暗号化チャネルのポストを復号して表示できる。
  - サーバーは包んだ鍵しか持たず、パスフレーズ・復旧キー・データ鍵の平文を受け取らない。
  - 初期設定は、暗号化チャネルを初めて作るときに行う。
- **端末ごとの鍵の扱い**: 解錠状態を端末に記憶するかを、端末ごとに利用者が選ぶ（既定は記憶しない）。
  - Electron は、OS の安全な保管領域に記憶できる。
  - ブラウザ / PWA は、取り出せない形の鍵として端末内に記憶できる。
  - 記憶しない端末は、15 分間操作が無いと自動でロックする（会社支給 Mac を想定）。
  - サインアウトしたら、端末に記憶した鍵を破棄する。
- **未解錠時の表示**: 解錠していない端末では、暗号化チャネルのポストを「ロック中」として表示し、本文を出さない。暗号化チャネルへの投稿・返信・編集も受け付けない。非暗号化チャネルは、ロックの状態に関係なく使える。チャネル名・投稿日時・リアクション・返信件数は平文のまま扱う。
- **添付**: 暗号化チャネルでは添付を付けられない（初版）。
- **下書き**: 暗号化チャネルの入力内容は、下書きとして端末のストレージに保存しない。メモリ上でだけ保持し、ロックやサインアウトで破棄する。
- **検索**: 暗号化チャネルのポストは、全文検索の対象にしない。
- **鍵の管理**: パスフレーズの変更と、復旧キーの再発行ができる。パスフレーズを忘れた場合は、復旧キーで解錠して新しいパスフレーズを設定する。両方を失うと復号できない。
- **API 契約**: 次を追加する。
  - チャネルに、暗号化チャネルかどうかの項目（作成時だけ指定できる）
  - ポストに、暗号文の項目
  - 包んだ鍵を取得・登録する API

### Non-goals

- 既存の非暗号化チャネルを、暗号化チャネルへ切り替えること（その逆も）。既存の秘匿メモは、暗号化チャネルを作って投稿し直す。
- 暗号化の有無を、親チャネルから子チャネルへ引き継ぐこと。
- 暗号化チャネルへの添付、および添付ファイルの暗号化。
- 暗号化チャネルのポストの全文検索（クライアント側での検索を含む）。
- パスキー（WebAuthn PRF）での解錠。初版はパスフレーズと復旧キーに限り、鍵の包み方は後から追加できる形にする。
- 利用者ごとの鍵、共有相手ごとの鍵。許可したアカウント全員が全データを共有する現行のモデルに合わせ、鍵はワークスペースで 1 つとする。
- チャネル名・投稿日時・リアクション・返信件数などのメタデータの暗号化。
- 端末そのもの（画面表示中のマルウェア・監視ソフト・XSS）からの保護。表示中の平文は端末上に存在する。

## Capabilities

### New Capabilities

- `channel-encryption`: 次の内容を扱う。
  - 暗号化チャネルの作成と、その不変性
  - 暗号化チャネルへの投稿・返信・編集と、表示
  - 鍵の初期設定・解錠・ロック・端末ごとの記憶
  - パスフレーズの変更と復旧
  - 削除との関係
  - サーバーが平文と鍵を受け取らないことの保証

### Modified Capabilities

- `full-text-search`: 「検索対象からの除外」に、暗号化チャネルのポストを検索結果に含めないことを追加する。
- `attachments`: 「ポストへの添付」に、暗号化チャネルでは添付を付けられないことを追加する。
- `post-composer`: 「下書きの保持」に、暗号化チャネルの入力内容を端末のストレージへ永続化しないことを追加する。

## Impact

- **Frontend**:
  - 暗号処理（WebCrypto の AES-GCM・PBKDF2・HKDF）の新規モジュールを追加する。
  - 鍵の状態（ロック中・解錠済み・未設定）を管理する。
  - 初期設定・解錠・パスフレーズ変更・復旧の画面を追加する。
  - チャネル作成時に暗号化を選べるようにし、チャネル一覧と見出しに印を付ける。
  - 暗号化チャネルの入力フォームを変える（暗号化の表示、添付の無効化、下書きをメモリにだけ持つ、ロック中は送信不可）。
  - タイムライン / スレッド / 編集フォームで、暗号化チャネルのポストを復号して表示する。
  - 自動ロックと、サインアウト時の鍵の破棄を入れる。
- **Platform adapter**: ブラウザでは、取り出せない形の鍵を IndexedDB に保持する。Electron では、既存の `secret:*`（`safeStorage`）に保持する。
- **Backend**:
  - マイグレーションで、`channels` に暗号化の有無の列、`posts` に暗号文の列を追加する。DB の制約で、ポストとチャネルの暗号化の有無の一致を保証する。
  - チャネル作成で暗号化の有無を受け取る。作成後は変更させない。
  - ポストの作成・返信・編集では、チャネルの暗号化の有無に応じて、平文と暗号文のどちらかだけを受け付ける。暗号化チャネルへの添付も拒否する。
  - 論理削除で暗号文も消去する。検索から暗号化チャネルを除く。
  - 包んだ鍵を保持するテーブルと API を追加する。
- **API 契約**: `api/openapi.yaml` を次のように変え、Go / TypeScript の生成物を再生成する。
  - `Channel` と `CreateChannelRequest` に、暗号化の有無の項目を追加する。
  - `Post`・`CreatePostRequest`・`EditPostRequest` に、暗号文の項目を追加する。
  - 鍵の API を追加する。
- **ドキュメント**: ARCHITECTURE.md（多層防御・暗号化チャネル）、DEPLOYMENT.md / SETUP_GUIDE.md（復旧キーの保管、端末ごとの運用）、README.md、API_REFERENCE.md、DATABASE_SCHEMA.md。
- **依存**: 追加しない（WebCrypto と既存の platform adapter を使う）。
- **前提**: `harden-sensitive-data-protection`（PR #38、マージ済み）の CSP・許可リスト・削除時の本文消去を前提にする。
