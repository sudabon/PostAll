## Context

入力フォーム周辺の実装は 3 ファイルに分かれている。

- `frontend/src/lib/fence.ts`（16 行）— `isInsideUnclosedFence` と `insertCodeFence`
- `frontend/src/lib/markdown-format.ts`（108 行）— 書式ツールバーの適用規則。`applyFormat` が囲み・リンク・行頭マーカー・コードブロックへ分岐する
- `frontend/src/components/composer/Composer.tsx`（430 行）— textarea 本体。`onChange` は `setValue` のみ、`onKeyDown` は Shift+Enter の送信のみを扱う（`Composer.tsx:324`）

既存の性質で、今回の設計が乗る土台になるもの。

- `insertCodeFence` は書式ツールバーの「コードブロック」ボタンからも `applyFormat('codeBlock', ...)` 経由で呼ばれる（`markdown-format.ts:36`）。**この 1 箇所を直せばツールバーと自動展開の挙動が揃う**
- `isInsideUnclosedFence` は `/^```/gm` で**行頭のフェンスだけ**を数える。自動展開の発火条件も行頭に揃えないと、判定の基準がずれる
- 書式ツールバーは既に `setValue` + `requestAnimationFrame` での `setSelectionRange` という手順でカーソルを操作している（`Composer.tsx:236` の `runFormat`）。同じ手順を再利用する
- `anyLineMarker = /^(?:[-*+] |\d+\. |> )/` と `applyLinePrefix` は**行頭固定**で、先頭に空白がある行を箇条書きと認識しない

制約として次がある。

- **Tab は textarea から抜ける唯一のキーボード手段**である。このアプリは送信が Shift+Enter なので Enter でも抜けられない。Tab を無条件に奪うと WCAG 2.1.2（キーボードトラップ）に該当する
- 本文はレンダリング側で `remark-gfm` + `remark-breaks` により解釈される（`components/markdown/MarkdownBody.tsx:38`）。入れ子の箇条書きに必要な字下げ量はこの構成が決める
- 入力中のライブプレビューは既存 spec が明確に禁止している。入力フォームはテキストのまま表示する

## Goals / Non-Goals

**Goals:**

- コードブロックの雛形を挿入した直後に、コードをそのまま打ち始められる
- 選択範囲を包んだとき、選択テキストが言語指定欄に入らない
- バッククォート 3 つでコードブロックが開き、閉じフェンスの打ち忘れが起きない
- 箇条書きの入れ子を Tab で作れる。字下げ量を利用者が数えなくてよい
- 上記を入れてもキーボードだけで入力フォームから抜けられる

**Non-Goals:**

- 入力中のシンタックスハイライトやライブプレビュー（既存 spec が禁止）
- Markdown エディタライブラリ（CodeMirror 等）への置き換え。素の textarea を維持する
- バッククォート 3 つ以外の自動展開（`- ` での箇条書き継続、`> ` での引用継続、対応括弧の自動補完など）
- 連番の振り直し。Markdown は `ol` の開始番号以外を無視するため、インデント時に番号を書き換えない
- コードフェンス内での Tab インデント。今回は箇条書きの行に限る
- 引用（`> `）の Tab インデント。引用の入れ子は空白ではなくマーカーの重ね（`> > `）で表すため、空白の増減では扱えない
- 自動展開を 1 操作で取り消す手段。ブラウザのネイティブ undo に委ねる

## Decisions

### カーソルは「フェンスに囲まれた本文の行」に置く

`insertCodeFence` を次のように変える。

| 入力 | 現在の結果 | 変更後 |
|---|---|---|
| 選択なし | `` ```\n``` `` / カーソルは開始フェンス直後 | `` ```\n\n``` `` / カーソルは中の空行 |
| 選択あり | `` ```<選択>\n``` `` / 選択が言語指定欄に入る | `` ```\n<選択>\n``` `` / カーソルは選択先頭 |

**理由**: 雛形を出した直後にまず書くのはコードである。言語指定を書きたいときは ↑ で 1 行戻れるが、コードを書きたいときに毎回 ↓ を押させる必要はない。頻度の高いほうを既定にする。

**選択ありの現在の結果は欠陥である。** `'```' + inner + '```'` で `inner` が選択テキスト + 改行になるため、選択したコードが情報文字列（言語名）として解釈され、コードブロックの中身が空になる。既存の単体テスト（`fence.test.ts:12`）は選択なしの経路しか通しておらず、素通りしている。同じ関数を触るので同じ変更で直す。

**ツールバーと自動展開は同じ関数を通す。** `applyFormat('codeBlock', ...)` が `insertCodeFence` へ委譲する構造は変えない。挙動の統一を呼び出し側の規約ではなく構造で保証する。

### 自動展開の検出は `onKeyDown` ではなく `onChange` の差分で行う

`lib/fence.ts` に純関数 `expandFenceTrigger(prev, next, caret)` を追加し、textarea の `onChange` から呼ぶ。以下を**すべて**満たすときだけ展開後の値とカーソルを返し、それ以外は `null` を返す。

1. `next.length === prev.length + 1` で、増えた 1 文字がバッククォートである
2. `next.slice(caret - 3, caret)` が バッククォート 3 つである
3. その 3 つが行頭から始まる
4. `isInsideUnclosedFence(prev, caret - 1)` が偽である

**`onKeyDown` を採らない理由**: キーイベントは予測変換・オートコンプリート・音声入力・ソフトキーボードの一部で発火しないか、`key` が `Unidentified` になる。値の差分を見れば入力経路によらず同じ判定になる。

**条件 1 が貼り付けと IME 確定を同時に排除する。** 貼り付けは 2 文字以上増える。IME の変換確定も確定文字列がまとめて入るため 1 文字にならない。バッククォート 1 文字だけを変換確定する経路は事実上ないが、保険として `onChange` は `isComposing` 中は展開しない。

**条件 3（行頭限定）の理由**: Markdown のフェンスは行頭でしか開かない。`isInsideUnclosedFence` も `/^```/gm` と行頭基準である。行の途中で展開すると、展開した結果が Markdown としてはコードブロックにならず、`isInsideUnclosedFence` も数えないという二重のずれが起きる。

**条件 4 の理由**: コードブロックの中身としてバッククォート 3 つを打ちたい場合、および閉じフェンスを手で打つ場合に、雛形が二重に挿入されるのを防ぐ。

### インデント幅は半角 4 つの固定とする

このプロジェクトのレンダリング構成（`remark-parse` + `remark-gfm` + `remark-breaks`、`MarkdownBody.tsx:38` と同一）で、親の記法と字下げ量の組み合わせを実測した。

| 親の記法 | +2 | +3 | +4 | +5 | +6 |
|---|---|---|---|---|---|
| `- foo` | 入れ子 | 入れ子 | **入れ子** | 入れ子 | 入れ子にならない |
| `* foo` | 入れ子 | 入れ子 | **入れ子** | 入れ子 | 入れ子にならない |
| `1. foo` | 別リストに分裂 | 入れ子 | **入れ子** | 入れ子 | 入れ子 |
| `10. foo` | 別リストに分裂 | 別リストに分裂 | **入れ子** | 入れ子 | 入れ子 |

CommonMark では入れ子に必要な字下げ量が親のマーカー幅で決まるため、記法ごとに下限が違う。一方 `- foo` は +6 で下限ではなく**上限**に当たり、入れ子にならなくなる。**4 と 5 だけが全記法で成立し、4 がその最小値**である。4 を採る。

2 段目以降も成立することを確認済み（`- a` / +4 `- b` / +8 `- c` で深さ 3、数字箇条書きでも同じ）。

**代替案（不採用）: 親のマーカー幅に合わせて 2〜4 を可変にする。** 見た目は締まるが、解除側が「1 段階戻す」ために各行の親を遡って幅を再計算する必要があり、複数行選択では行ごとに異なる幅を扱うことになる。字下げ量が不揃いだと利用者が手で直したときに壊れやすい。固定幅なら増減が単純な文字列操作で完結する。

**タブ文字（`\t`）を使わない理由**: CommonMark はタブを 4 桁のタブストップとして展開するため入れ子自体は成立するが、textarea 上の表示幅がブラウザ設定に依存し、他のクライアントや `git diff` での見え方も揃わない。空白で書き出す。

### Tab を奪うのは「箇条書きの行」に限る

`lib/markdown-format.ts` に `indentLines(value, start, end, { outdent })` を追加し、選択範囲にかかる全行を見て判定する。

**Tab（インデント）**

- 対象行が**すべて**箇条書きマーカー（先頭空白を許した `- ` `* ` `+ ` `1. ` 等）で始まる → `preventDefault()` して全行をインデント
- 1 行でも該当しない → **何もしない。** ブラウザ既定のフォーカス移動が起きる

**Shift+Tab（インデント解除）— Tab の逆操作**

- 対象行がすべて箇条書きで、かつ**1 行でも 1 段階以上インデントされている** → `preventDefault()` して、インデントされている行だけを 1 段階解除する
- 解除できる行が 1 つも無い → **何もしない。** 逆方向のフォーカス移動が起きる

**往復性を要件として持たせる。** Tab を押した直後の Shift+Tab は、本文を Tab を押す前と同一に戻す。`indentLines` の増減を同じ字下げ単位（半角 4 つ）で対称に実装すれば自然に満たせるが、単一行と複数行の両方でテストして固定する。

**混在した選択の扱いが Tab と Shift+Tab で非対称なのは意図的である。**

| | 混在の中身 | 挙動 | 理由 |
|---|---|---|---|
| Tab | 箇条書き + 箇条書きでない行 | 何もしない | 文章の行に空白が入ると本人の意図しない字下げになる。Markdown では 4 つの字下げがコードブロックの合図にもなるため、黙って壊れる |
| Shift+Tab | インデント済み + インデント無しの箇条書き | 解除できる行だけ解除 | すべて箇条書きなので壊れる行が無い。インデント 0 の行は下限で止まるだけで、実害が無い |

Shift+Tab を Tab と同じ「全行が条件を満たすときだけ」にすると、入れ子の途中から選択した一般的なケース（親と子をまとめて選ぶ）で毎回フォーカスが飛び、解除できなくなる。逆に Tab を「該当する行だけ」にすると、上の表のとおり黙って本文を壊す。**壊れる側を厳しく、壊れない側を緩くする**という基準で分けている。

**理由**: これでフォーカスが閉じ込められる状況が構造的に存在しなくなる。空のフォーム、通常の文章、コードブロックの中—どれも箇条書きではないので Tab は必ず抜ける。「Esc を押してから Tab で抜ける」といった追加の脱出規約を利用者に覚えさせずに済む。Esc は既に編集モードの取り消しに割り当て済みで、二重の意味を持たせたくない。

**代替案（不採用）: 未閉コードフェンスの中で Tab をインデントにする。** `isInsideUnclosedFence` があるので実装は容易だが、コードブロックはフォームの中で最も長く滞在する場所であり、そこで Tab が抜けられないのは影響が大きい。今回は入れる理由がない。

### `anyLineMarker` と `applyLinePrefix` を先頭インデント対応にする

現在 `anyLineMarker = /^(?:[-*+] |\d+\. |> )/` は行頭固定なので、`    - foo` を箇条書きと認識しない。この状態でツールバーの箇条書きボタンを押すと、マーカーが剥がれずに `-     - foo` になる。

先頭空白を捕獲して保持したままマーカーだけを判定・付け替えるよう変える。**これは今回の変更で初めて到達可能になる経路である**（インデントされた箇条書きを作る手段が今まで無かった）。同じ変更に含めないと、Tab を入れた瞬間にツールバーが壊れる。

**`anyLineMarker` を `indentLines` から流用してはならない。** `anyLineMarker` は引用（`> `）を含むが、引用は Tab の対象外である（Resolved Questions 2）。`indentLines` は `- ` `* ` `+ ` `1. ` だけを見る独自の判定を持ち、引用の行に対しては `null` を返してフォーカス移動に任せる。似た正規表現が 2 つ並ぶことになるが、**用途が違う**（一方は「行頭マーカーを剥がす対象」、他方は「空白の増減で入れ子にできる対象」）ため、共通化すると引用が誤って字下げされる。それぞれの意図をコメントで残す。

## Risks / Trade-offs

**`setValue` による書き換えでブラウザのネイティブ undo 履歴が切れる。** 自動展開後に Cmd+Z を押しても、展開前（バッククォート 3 つ）には戻らず、それ以前の状態まで飛ぶ。書式ツールバーが既に同じ挙動なので新しい種類のリスクではないが、**ツールバーは押した本人が意図した操作であるのに対し、自動展開は打っている最中に起きる**ぶん、取り消したくなる頻度が高い。**専用の取り消し手段は用意しない**（Resolved Questions 1）。状態を増やさずに出し、実際に困るかを見てから判断する。

**バッククォート 3 つを素で書きたい場合に邪魔になる。** 行頭でバッククォート 3 つを打つ意図が「コードブロックを開く」以外にあるケースは、コードブロックの書き方そのものを説明する文章に限られる。取り消し手段を持たないため、その場合は挿入された閉じフェンスと改行を手で消すことになる。コードブロックの中では展開しない（条件 4）ので、コードブロックの書き方を説明する文章はその中に書けば影響を受けない。許容する。

**インデント 4 は見た目が深い。** 手書きの Markdown は 2 で書く人が多く、4 は冗長に見える。ただし数字箇条書きが 2 で壊れることのほうが実害が大きい。

## Migration Plan

移行手順は不要。保存済みの本文には触れず、生成する Markdown も従来どおり解釈できる範囲に収まる。既存の投稿の表示は変わらない。

## Resolved Questions

1. **自動展開の取り消し手段を用意するか → 用意しない。** 展開直後の Backspace で展開前へ戻す特別扱いは入れず、ブラウザのネイティブ undo に委ねる。「直前の操作が自動展開だったか」を覚える状態を増やさずに済む。undo 履歴が切れる件は Risks / Trade-offs に残す。実際に困るかを見てから改めて判断する。

2. **Tab の対象に引用（`> `）を含めるか → 含めない。** 引用の入れ子は空白ではなくマーカーの重ね（`> > `）で表すため、空白の増減を行う `indentLines` では扱えない。引用の行は「箇条書き以外の行」として扱い、Tab / Shift+Tab は従来どおりフォーカスを移す。実装上は `anyLineMarker`（引用を含む）を `indentLines` へ流用しないことが要点で、Decisions に記載した。
