## ADDED Requirements

### Requirement: スタンプ画像のアップロード登録
システムは、サインイン済みユーザーが画像をアップロードしてカスタム絵文字（スタンプ）をカタログへ登録できるようにしなければならない (SHALL)。サーバは、認可・画像形式・画像サイズ・ショートコードの妥当性・ショートコードの一意性を検証したうえで登録しなければならない (SHALL)。いずれかの検証を満たさない要求で登録を成立させてはならない (MUST NOT)。受け付ける形式は PNG と GIF でなければならない (SHALL)。1 ファイルあたりの上限サイズを設けなければならない (SHALL)。

#### Scenario: PNG を登録する
- **WHEN** サインイン済みユーザーが PNG 画像とショートコードを伴って登録を要求する
- **THEN** システムは実体をオブジェクトストレージへ配置し、ショートコード・保存キー・チェックサムをカタログへ記録し、当該スタンプをリアクションとして選択可能にする

#### Scenario: アニメーション GIF を登録する
- **WHEN** サインイン済みユーザーがアニメーションを含む GIF 画像で登録を要求する
- **THEN** システムは当該画像を登録し、リアクションおよびピッカーでの表示時にアニメーションを保ったまま表示する

#### Scenario: 対応していない形式を拒否する
- **WHEN** PNG でも GIF でもない形式のファイルで登録が要求される
- **THEN** サーバは登録せず、対応している形式を示すエラーを返し、カタログを変更しない

#### Scenario: 申告と実体の形式が食い違う
- **WHEN** 拡張子または申告された形式が PNG／GIF でありながら、実体の中身がそのいずれでもないファイルで登録が要求される
- **THEN** サーバは実体の中身を根拠に判定し、当該要求を登録せず、エラーを返す

#### Scenario: 上限サイズを超える画像
- **WHEN** 上限サイズを超える画像で登録が要求される
- **THEN** サーバは登録せず、上限値を含むエラーを返す

#### Scenario: クライアント側でも制約を先に検証する
- **WHEN** ユーザーが対応形式外または上限サイズ超過のファイルを選択する
- **THEN** システムはアップロードを開始せず、その場で理由と上限値を提示する

#### Scenario: ショートコードが既存と重複する
- **WHEN** 既にカタログに存在するショートコードで登録が要求される
- **THEN** サーバは登録せず、既存のスタンプの画像・ショートコードの結び付きを一切変更せず、重複している旨をユーザーへ提示できる形で返す

#### Scenario: ショートコードとして不正な値
- **WHEN** ショートコードとして使えない文字を含む、または長さの上限を超えるショートコードで登録が要求される
- **THEN** サーバは登録せず、使える文字と長さの条件を示すエラーを返す

#### Scenario: 認可されていない登録要求
- **WHEN** 認可情報を伴わない要求がスタンプの登録を求める
- **THEN** サーバは要求を拒否し、実体を配置せず、カタログを変更しない

#### Scenario: 実体の配置後にカタログへの記録が失敗する
- **WHEN** 実体をオブジェクトストレージへ配置した後、カタログへの記録が失敗する
- **THEN** システムは当該ショートコードを一覧に現れる状態にせず、同じショートコードでの再登録を妨げない

### Requirement: 登録するスタンプのショートコードの決定
システムは、選択された画像ファイルのファイル名（拡張子を除いた部分）からショートコードの初期値を導出しなければならない (SHALL)。ユーザーは登録を確定する前にショートコードを修正できなければならない (SHALL)。

#### Scenario: ファイル名からショートコードを導出する
- **WHEN** ユーザーがスタンプにする画像ファイルを選択する
- **THEN** システムはファイル名の拡張子を除いた部分をショートコードの初期値として提示する

#### Scenario: ショートコードを修正して登録する
- **WHEN** ユーザーが提示されたショートコードを書き換えて登録を確定する
- **THEN** システムは書き換えた後のショートコードで登録する

#### Scenario: ファイル名からショートコードを導出できない
- **WHEN** 選択されたファイル名が、ショートコードとして使える形に整えられない
- **THEN** システムはショートコードを空の状態で提示して入力を促し、妥当なショートコードが入るまで登録を確定できないようにする

### Requirement: スタンプ登録の進行と失敗時の扱い
システムは、スタンプ登録の進行中であることを提示し、同一の登録操作が重複して実行されないようにしなければならない (SHALL)。登録が失敗した場合は、理由を提示し、入力内容を保ったまま再試行できるようにしなければならない (SHALL)。

#### Scenario: 登録中の表示
- **WHEN** スタンプの登録が進行中である
- **THEN** システムは進行中であることを提示し、完了または失敗までは同じ登録操作を受け付けない

#### Scenario: 登録操作の二重実行
- **WHEN** ユーザーが登録の確定操作を短時間に繰り返す
- **THEN** システムは登録要求を 1 件しか送らず、同じ画像から重複したスタンプを作らない

#### Scenario: 登録が失敗する
- **WHEN** 登録がネットワークまたはサーバのエラーで失敗する
- **THEN** システムは失敗した旨と理由を提示し、選択済みの画像とショートコードを保持したまま再試行できるようにする

## MODIFIED Requirements

### Requirement: カスタム絵文字カタログ
システムは、`emoji/` ディレクトリに配置された png ファイルをカスタム絵文字としてカタログに登録しなければならない (SHALL)。ショートコードは png のファイル名（拡張子を除いた部分）から導出されなければならない (SHALL)。登録処理は、png の実体をオブジェクトストレージへ配置し、データベースにはショートコード・保存キー・チェックサムのみを記録しなければならない (SHALL)。`emoji/` ディレクトリの走査による一括登録は、要求の処理経路ではなく、デプロイ工程で実行されなければならない (SHALL)。カタログへの登録経路はこの一括登録に限られず、要求経路からの 1 件単位の登録も認められる。どちらの経路で登録されたスタンプも、リアクションとしての扱いに差があってはならない (MUST NOT)。

#### Scenario: png を登録する
- **WHEN** 登録処理が `emoji/` ディレクトリを走査し、未登録の png を検出する
- **THEN** システムはファイル名から導出したショートコードで当該絵文字をカタログへ登録し、実体をオブジェクトストレージへ配置し、リアクションとして選択可能にする

#### Scenario: 内容が変わった png を再登録する
- **WHEN** 既に登録済みのショートコードと同じファイル名で、内容（チェックサム）が異なる png が検出される
- **THEN** システムは当該絵文字の実体を更新し、既存のリアクションのショートコードとの結び付きを維持する

#### Scenario: 内容が同じ png を再走査する
- **WHEN** 登録処理が、既に登録済みで内容も同一の png を再度検出する
- **THEN** システムは重複した登録を作らず、カタログを変更せず、実体の再配置も行わない

#### Scenario: png 以外のファイルを無視する
- **WHEN** `emoji/` ディレクトリに png 以外のファイルが含まれる
- **THEN** システムは当該ファイルを登録せず、処理を中断しない

#### Scenario: ショートコードとして不正なファイル名
- **WHEN** ショートコードとして使えない文字を含むファイル名の png が検出される
- **THEN** システムは当該ファイルの登録を行わず、その旨を記録したうえで他のファイルの登録を続行する

#### Scenario: 登録処理は API サーバの起動に依存しない
- **WHEN** API サーバの新しいインスタンスが起動する
- **THEN** システムは `emoji/` ディレクトリの走査を行わず、既にカタログへ登録済みの内容を用いる

#### Scenario: 要求経路で登録されたスタンプを一括登録が壊さない
- **WHEN** 要求経路から登録されたスタンプがカタログに存在する状態で、`emoji/` ディレクトリの一括登録が実行される
- **THEN** システムは当該スタンプのカタログ登録とリアクションとの結び付きを維持し、`emoji/` に同じショートコードのファイルが無い限り実体も変更しない

### Requirement: 絵文字の一覧と選択
システムは、登録済みの絵文字を一覧し、ポストへのリアクションとして選択できる UI を提供しなければならない (SHALL)。この UI は、新しいスタンプ画像をアップロードして登録を開始する操作を提供しなければならない (SHALL)。

#### Scenario: 絵文字ピッカーを開く
- **WHEN** ユーザーがポストのリアクション追加操作を実行する
- **THEN** システムは登録済み絵文字の一覧をショートコード付きで表示する

#### Scenario: 絵文字を絞り込む
- **WHEN** ユーザーが絵文字ピッカーでショートコードの一部を入力する
- **THEN** システムは一致する絵文字のみに一覧を絞り込む

#### Scenario: 絵文字が 1 件も登録されていない
- **WHEN** カタログに絵文字が 1 件も存在しない状態でピッカーを開く
- **THEN** システムは絵文字が未登録である旨を表示し、エラーとして扱わず、スタンプを追加する操作は引き続き提供する

#### Scenario: ピッカーから登録を開始する
- **WHEN** ユーザーが絵文字ピッカーでスタンプの追加操作を実行する
- **THEN** システムは画像ファイルの選択とショートコードの確認を伴う登録の手順を提示する

#### Scenario: 登録直後に一覧へ反映する
- **WHEN** ピッカーからのスタンプ登録が成功する
- **THEN** システムは再読み込みの操作を求めずに、登録されたスタンプを同じピッカーの一覧に現れる状態にする

#### Scenario: 登録したスタンプをそのままリアクションに使う
- **WHEN** ユーザーが登録直後のスタンプを一覧から選択する
- **THEN** システムは当該スタンプのリアクションをポストへ付与する

### Requirement: 絵文字画像の配信
システムは、登録済みの絵文字画像を、認可を検証したうえで取得できるようにしなければならない (SHALL)。画像の実体を API サーバのローカルファイルシステムから配信してはならない (MUST NOT)。取得の応答は、当該画像の形式をクライアントが判別できる形で示さなければならない (SHALL)。

#### Scenario: 絵文字画像を取得する
- **WHEN** クライアントがショートコードを指定して絵文字画像を要求する
- **THEN** システムは認可を検証したうえで、当該ショートコードに対応する画像の内容と、その形式を示す情報を取得できるようにする

#### Scenario: 認可されていない取得要求
- **WHEN** 認可情報を伴わない要求が絵文字画像を求める
- **THEN** サーバは要求を拒否し、画像を取得できるようにしない

#### Scenario: 登録されていないショートコード
- **WHEN** カタログに存在しないショートコードで画像が要求される
- **THEN** システムは見つからない旨を返し、他のオブジェクトの内容を返さない

#### Scenario: 内容が変わっていない画像を再取得する
- **WHEN** クライアントが取得済みの絵文字画像を、直前に得た検証子とともに再要求する
- **THEN** システムは内容が変わっていない場合に本体を再送せず、再利用してよいことを示す

#### Scenario: 絵文字の実体が失われている
- **WHEN** カタログに登録済みだが、オブジェクトストレージに実体が存在しないショートコードで画像が要求される
- **THEN** システムは見つからない旨を返し、一覧全体の取得を失敗させない
