## Context

動機は proposal.md - Why を参照。以下は approach を決める上で効いている現状の制約。

- カタログの登録経路は `postall-server emoji-sync` の 1 本のみ。`emoji/` を走査し、png だけを Storage へ Put して `emojis` へ upsert する（`backend/internal/emoji/service.go`）。gif は「PNG ファイルではありません」として skip される。
- `emojis` は `id / shortcode(UNIQUE) / storage_key / checksum / created_at`。`storage_key` は一括登録では `emoji/` 内のファイル名そのもの。
- API サーバは既に `EMOJI_S3_BUCKET` の `blob.Store`（`s.emojiBlobs`）を持ち、`emoji-sync` と同じ `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` で初期化される。したがって要求経路からの Put に新しい資格情報は要らない。
- 画像の配信は `GET /v1/emojis/{shortcode}/image` が API サーバ経由でストリームする（署名付き URL へのリダイレクトはしない）。応答の `Content-Type` は Storage 上のオブジェクトの content type、空なら `image/png` にフォールバックする。
- フロントの `ApiClient.request` は JSON 専用（`init.json` を `JSON.stringify` して `Content-Type: application/json` を付ける）。`FormData` を送る経路は存在しない。
- ピッカーは `<dialog>` + `useOverlayPresence` でフォーカスと退場アニメーションを管理する単一のオーバーレイ。
- 既存 `emoji/` の最大ファイルは `celebrate.gif` の約 102 KiB。

## Goals / Non-Goals

**Goals:**

- 実体の配置とカタログ行の作成を 1 回の要求で確定させ、「途中状態」を持たない。
- 形式の判定を、クライアントの申告ではなく実体の中身に基づいて行う。
- 既存の一括登録経路のふるまいと、既存の `emojis` テーブル定義を変えない（マイグレーションなし）。
- ショートコードの妥当性規則を一括登録と要求経路で 1 箇所に持つ。

**Non-Goals:**

- 実体が残ったままカタログ行が作られなかったオブジェクト（orphan）の自動回収。
- `emoji/` と要求経路のどちらで登録されたかを区別するデータモデル（カラム追加）。
- 画像の再エンコード・リサイズ・アニメーション除去・寸法の検証。

## Decisions

### D1. アップロードは署名付き URL の 2 フェーズではなく、API を通す 1 要求にする

`POST /v1/emojis` に `multipart/form-data`（`shortcode` と `file`）を送り、サーバが検証 → Storage へ Put → `emojis` へ insert → `201` で `Emoji` を返す。

**理由**:

1. スタンプは上限 512 KiB（D3）の小さいファイルで、Vercel の関数のリクエストボディ上限（4.5 MB）に十分収まる。添付が署名付き URL を採るのは実体が大きく、ポストとの紐付けが後追いになるためで、スタンプには当てはまらない。
2. 「実体を置く」と「カタログ行を作る」が同時に確定してこそ意味がある。2 フェーズにすると未確定オブジェクトの状態と回収ジョブを設計する必要が出る（添付の spec が「完了が通知されない」シナリオを持つのはそのため）。
3. 署名付き URL ではサーバは申告された content type と size しか検証できない。実体を受け取れば中身のマジックバイトで判定できる（D3）。
4. emoji の実体は既に GET で API を通っている。「実体は API サーバを経由してはならない」という制約は `attachments` capability の要件であって、`emoji-reactions` には無い。

**代替**: `POST /v1/emojis/uploads` → 署名付き PUT → `POST /v1/emojis/{id}/complete`。添付と経路が揃うが、未確定状態・回収・中身の検証不能という 3 つのコストを、512 KiB のファイルのために払うことになる。却下。

### D2. OpenAPI に multipart で宣言し、ハンドラは `r.ParseMultipartForm` で読む

oapi-codegen は JSON 以外の requestBody に対して本文の型を生成しないため、ハンドラの引数からは本文が消える。契約は `api/openapi.yaml` に `content: multipart/form-data` として残し（`shortcode`: string、`file`: `type: string, format: binary`）、読み取りはハンドラ側で行う。応答 `201` は既存の `Emoji` スキーマを再利用する。

**トレードオフ**: 生成物が本文の型を持たないので、契約と実装の一致は生成器ではなくハンドラのテストで担保する。`frontend/src/api/schema.d.ts` 側も本文の型は使えないため、クライアントは `FormData` を手で組む。

### D3. 形式は実体のマジックバイトで判定し、上限は 512 KiB

- 読み取りは `http.MaxBytesReader` で 512 KiB + 余白に制限し、上限超過は読み取り段階で落とす（メモリに全部載せてから測らない）。
- `http.DetectContentType`（先頭 512 バイト）が `image/png` または `image/gif` を返すものだけを受理する。ファイル名の拡張子とクライアントの `Content-Type` は判定に使わない。
- Storage へ Put する content type は判定結果を使う。これで GIF は `image/gif` として保存され、既存の `GetEmojiImage` がそのまま `image/gif` を返し、`EmojiImage` の `<img>` でアニメーションする（配信側の変更は不要）。

**512 KiB の根拠**: 既存 `emoji/` の最大が約 102 KiB、`emoji/` 全体で 876 KiB。5 倍の余裕があれば実用上足り、Vercel の本文上限にも遠い。上限値はサーバ側の定数を単一の正とし、エラーメッセージに数値を含める。クライアントは同じ値を持って事前に弾く（二重に持つが、サーバが最終権限を持つ）。

### D4. ショートコードの規則は既存パターンを共有し、導出はクライアントで行う

- サーバの検証は `internal/emoji` の既存 `shortcodePattern`（`^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`）をそのまま使う。一括登録と要求経路で規則が食い違わないよう、パッケージから公開して両方が同じものを参照する。
- クライアントの初期値の導出: 拡張子を除去 → 小文字化 → `[A-Za-z0-9_-]` 以外を `-` に置換 → 連続する `-` を 1 つに畳む → 先頭が英数字になるまで先頭を削る → 64 文字で切る → 末尾の `-`/`_` を削る。結果が空なら空欄で提示し、入力を促す。
- サーバは導出結果を信用せず、受け取った値をパターンで検証する。

**理由**: 導出はユーザーが目で確認して直せる「たたき台」であり、正規化の細かい挙動が UI 側の都合で変わっても契約は壊れない。サーバはパターンだけを守らせる。

### D5. 要求経路の `storage_key` は `emojis/<uuid>.<ext>` にする（ファイル名キーにしない）

**理由**: `storage_key` を `<shortcode>.<ext>` にすると、既存ショートコードと重複する登録要求で「Put が先に既存オブジェクトを上書きし、その後 insert が重複で失敗する」という順序になり、「既存のスタンプの画像を一切変更しない」という要件を破る。オブジェクトキーを登録ごとに一意にすれば、Put が既存の実体に触れることが構造的に無くなる。

- 一括登録は従来どおりファイル名キー（`arigatou.png`）のまま。両者のキー空間が重ならないよう、要求経路は `emojis/` プレフィックス配下に置く。
- `GetEmojiImage` は `storage_key` をそのまま使うだけなので、キーの形が混在しても配信は変わらない。

**代替**: `<shortcode>.<ext>` + 事前 SELECT で重複を弾く。単独の SELECT は競合で破れるうえ、破れたときに既存画像を壊すのが最悪の失敗になる。却下。

### D6. 重複はデータベースの UNIQUE 制約で判定する

`InsertEmoji` の unique violation（`pgErr.Code == "23505"`）を `409` の `shortcode_conflict` にマップする。`channel` サービスが同名チャネルで採っているのと同じ手当て。事前の存在確認は UI のための早期フィードバックとしてのみ使い、判定の正はデータベースに置く。

処理順は **Put → insert**。insert が失敗した場合、`emojis/<uuid>.<ext>` のオブジェクトだけが残るが、`storage_key` を指す行が無いため一覧にも配信にも現れず、同じショートコードでの再登録も妨げない（spec の「実体の配置後にカタログへの記録が失敗する」を満たす）。orphan の回収は Non-Goal。

**代替**: insert → Put。Put が失敗するとカタログに実体の無い行が残り、一覧に「壊れたスタンプ」が並ぶ。orphan オブジェクトより害が大きい。却下。

### D7. 認可はサインイン済みであることのみ。アップロード者は記録しない

既存の `authorFrom(w, r)` を使う（未認証は既存のミドルウェアが弾く）。`emojis` にアップロード者のカラムは足さない。

**理由**: 権限区分と削除は今回のスコープ外（proposal - スコープに含めないもの）。カラムだけ先に足しても使う要件が無く、マイグレーションを増やす分だけ損。削除や監査が必要になった時点で、その change がカラムと一緒に要件を持ち込む。

### D8. 登録後の反映は `['emojis']` の invalidate。楽観挿入はしない

カタログのクエリは `staleTime: 5 * 60 * 1000` を持つため、成功時に `queryClient.invalidateQueries({ queryKey: ['emojis'] })` を明示的に呼ぶ。

**理由**: 一覧に出すには `id` / `checksum` / `imagePath` が必要で、これらはサーバが決める。ローカルのファイルから `Emoji` を組み立てて先に差し込むと、`EmojiImage` の `['emoji-image', shortcode, checksum]` キーが確定前の値で埋まる。登録の応答は数百 ms で返るので楽観化の利得が小さい。ポスト編集の楽観更新（`f23fde8`）とは、待ち時間と入力コストの釣り合いが違う。

### D9. UI はピッカーのダイアログ内での面の切り替えにする（別ダイアログを重ねない）

- 一覧のヘッダに「スタンプを追加」ボタンを置き、押すと同じ `<dialog>` の中身が登録パネルに切り替わる。パネルには「戻る」がある。
- ファイル選択はネイティブの `<input type="file" accept="image/png,image/gif">` を視覚的に隠して `<label>`（またはボタン + `ref.click()`）で開く。
- プレビューは `URL.createObjectURL` で表示し、選択が変わった時と離脱時に `revokeObjectURL` する。URL はファイル選択のイベントハンドラで作るため、D10 の StrictMode の問題は起きない（マウント後に選択が起きるので、effect の cleanup が生きた URL を消すことがない）。
- 登録中はボタンを `disabled` にして二重送信を防ぐ。失敗時はエラー文言を出し、選択済みファイルとショートコードを保持する。

**理由**: `<dialog>` を入れ子にすると `useOverlayPresence` のフォーカス復帰と `onCancel` の扱いが二重になり、Esc がどちらを閉じるかが曖昧になる。同じダイアログ内の面の切り替えなら、既存のフォーカス管理をそのまま使える。

**代替**: ピッカーとは独立した「スタンプ管理」画面。将来削除や一覧管理を入れるならそちらが素直だが、今回の要件は「ピッカーを開いたその場で追加できること」なので、導線を別画面に出すと動機を満たさない。却下。

### D10. 実装中に見つけた `EmojiImage` のオブジェクト URL のバグを本 change で直す

`BlobImage` は URL を `useState` の初期化子で作り、effect の cleanup で revoke していた。`main.tsx` が `<StrictMode>` で包んでいるため、開発ビルドでは effect が setup → cleanup → setup で回り、マウントしたままの `img` が revoke 済みの URL を指す。結果、開発サーバ上では**すべてのカスタム絵文字画像が読めず**ショートコードのテキストにフォールバックしていた（本番ビルドは effect を二重に走らせないため表面化していなかった）。

オブジェクト URL を blob に紐づけた `WeakMap` で 1 つだけ持ち、revoke をやめる。二重描画でも、ピッカーの開閉による再マウントでも同じ URL を返すため、URL は「描画されたことのある (ショートコード, チェックサム) の数」で上限される。

**理由**: 本 change のスコープ外の既存バグだが、GIF が画像として表示されることを E2E で観測できない（TP-012 が通らない）という形でこの change に直接ぶつかる。revoke をやめるだけでは再マウントごとに URL が増え、URL を state に持って effect で作る形は `react-hooks/set-state-in-effect` に触れる。blob ごとに 1 つという形が、StrictMode の二重実行と再マウントの両方に対して素直に正しい。

## Risks / Trade-offs

- **誰でも登録でき、消す手段が UI に無い** → 不適切な画像やショートコードの汚染は、当面 `emojis` の行と Storage のオブジェクトを直接消す運用で対処する。削除 UI は次の change として切り出す。小規模な社内チームという前提でこのリスクを受け入れる。
- **orphan オブジェクトが溜まる** → insert 失敗時のみ発生し、1 件あたり最大 512 KiB。カタログに現れないので機能上の害は無い。回収が必要になるほど溜まるかを、しばらく運用して見る。
- **形式の判定を先頭 512 バイトに頼る** → PNG / GIF のシグネチャは先頭 8 バイト以内にあるため判定自体は堅い。一方、壊れた（シグネチャだけ正しい）画像は通ってしまい、表示時に `EmojiImage` のフォールバックでショートコードのテキストになる。デコードまでの検証はしない。
- **上限値をサーバとクライアントの 2 箇所に持つ** → ずれると「クライアントは通すがサーバが弾く」または逆になる。サーバの応答が最終権限であることをエラー表示で担保し、値は双方でテストに書いて固定する。
- **`emoji/` に同じショートコードの png が後から入ると、一括登録が要求経路のスタンプの実体を差し替える** → 既存の「内容が変わった png を再登録する」ふるまいそのままで、リポジトリ側が勝つ。ショートコードとリアクションの結び付きは維持されるため、spec の要件は満たす。区別が必要になったら由来を持つカラムを入れる change を立てる。
- **絵文字のオブジェクト URL を revoke しない**（D10） → 描画された絵文字 1 件につき URL が 1 つ、ページの寿命の間残る。カタログの件数で上限されるため実用上問題にならないが、カタログが数千件規模になったら見直す。
- **multipart の本文が生成物の型を通らない** → 契約と実装のずれを生成器が検出できない。ハンドラのテストで形式・サイズ・重複・不正ショートコードの各経路を押さえる。

## Migration Plan

- データベースのマイグレーションは無い（`emojis` の定義を変えない）。
- `make generate`（Go）と `npm run generate`（TS）で生成物を更新する。CI が `git diff --exit-code` で追従漏れを落とす。
- 新しい環境変数は無い。`EMOJI_S3_BUCKET` と `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` は既に設定済みで、`emoji-sync` が同じ資格情報で Put しているため書き込み権限も確認済み。デプロイ前に、API サーバの実行環境で `EMOJI_S3_BUCKET` が設定されていることだけ確認する（未設定だと `s.emojiBlobs` が nil になり、登録は `503` を返す）。
- デプロイ順は API → frontend。frontend が先に出ると「スタンプを追加」ボタンが 404 になる。
- ロールバックは frontend を前のバージョンへ戻せば導線が消える。API を残しても既存クライアントは呼ばない。既に登録されたスタンプはカタログに残り、リアクションとして機能し続ける（無害）。
