## ADDED Requirements

### Requirement: 単一の source of truth
システムは、チャネル・ポスト・添付・リアクションのすべてを Go バックエンドと PostgreSQL（添付の実体は S3）に保持し、各クライアントはこれを唯一の正とみなさなければならない (SHALL)。

#### Scenario: 各クライアントで同じ内容を見る
- **WHEN** Electron・ブラウザ・iOS が同一のバックエンドへ接続し、同じチャネルを開く
- **THEN** システムはいずれにも同一のチャネル階層とポスト一覧を提供する

#### Scenario: 片方の変更がもう片方に届く
- **WHEN** デスクトップでチャネルの階層を変更する
- **THEN** iOS は次回のデータ取得時に変更後の階層を表示する

### Requirement: HTTP API 契約
システムは、チャネル・ポスト・スレッド・リアクション・添付・検索に対する操作を HTTP API として提供しなければならない (SHALL)。API はすべてのクライアントで共通でなければならない (SHALL)。エラーは機械可読なコードと人間可読なメッセージを含む一貫した形式で返さなければならない (SHALL)。

#### Scenario: チャネル一覧を取得する
- **WHEN** クライアントがチャネル一覧の取得を要求する
- **THEN** システムは階層関係と並び順を復元できる形式でチャネル全体を返す

#### Scenario: ポストを範囲指定で取得する
- **WHEN** クライアントがチャネル ID と位置カーソル、件数を指定してポストの取得を要求する
- **THEN** システムは作成日時の昇順で指定件数のポストと、続きを取得するためのカーソルを返す

#### Scenario: 不正な要求を拒否する
- **WHEN** クライアントが必須項目を欠いた要求、または存在しない ID を指定した要求を送る
- **THEN** システムは対応する HTTP ステータスと、一貫した形式のエラー本文を返す

#### Scenario: 想定外のサーバーエラー
- **WHEN** サーバー内部で想定外のエラーが発生する
- **THEN** システムは内部実装の詳細を漏らさないエラー本文を返し、サーバー側にはエラーの詳細を記録する

### Requirement: データモデルの永続化
システムは、チャネルの階層と並び順、ポストの本文と日時、スレッドの親子関係、リアクション、添付のメタデータを PostgreSQL に永続化しなければならない (SHALL)。スキーマの変更はマイグレーションとして版管理されなければならない (SHALL)。

#### Scenario: 再起動後もデータが残る
- **WHEN** バックエンドのコンテナを停止して再起動する
- **THEN** システムは停止前のチャネル階層・ポスト・スレッド・リアクション・添付をすべて保持している

#### Scenario: マイグレーションを適用する
- **WHEN** 新しいスキーマ版を含むバックエンドを未適用の DB に対して起動する
- **THEN** システムは未適用のマイグレーションを検出し、適用するか、適用が必要である旨を明示して停止する

#### Scenario: 参照整合性を保つ
- **WHEN** チャネルまたはポストが削除される
- **THEN** システムは、それに紐づくスレッド・リアクション・添付が不整合な状態で残らないよう一貫した状態を維持する

### Requirement: 階層移動の原子性
システムは、チャネルの親付け替えおよび並び替えを原子的に適用しなければならない (SHALL)。処理が中断した場合に階層が不整合な状態で残ってはならない (MUST NOT)。

#### Scenario: 移動処理が途中で失敗する
- **WHEN** チャネル移動の処理中にエラーが発生する
- **THEN** システムは変更を巻き戻し、移動前の階層と並び順を維持する

#### Scenario: 循環を作る移動を拒否する
- **WHEN** チャネルを自身の子孫を親とするよう変更する要求が届く
- **THEN** システムは要求を拒否し、階層を変更しない

#### Scenario: 移動結果の順序キーを返す
- **WHEN** クライアントがチャネルの移動を要求する
- **THEN** サーバは適用後の親と順序キーを応答に含め、クライアントがそれを正として自身の状態を更新できるようにする

### Requirement: 変更の反映
システムは、他クライアントによる変更を、表示中のクライアントへ反映する手段を提供しなければならない (SHALL)。

#### Scenario: 表示中チャネルへの新規ポスト
- **WHEN** あるクライアントが表示中のチャネルへ、別のクライアントがポストを追加する
- **THEN** システムは表示中クライアントのタイムラインへ当該ポストを追加する

#### Scenario: 再接続時に取りこぼしを埋める
- **WHEN** クライアントが一時的に接続を失い、その後再接続する
- **THEN** システムは切断中に発生した変更をクライアントが取得できるようにし、表示を最新化する

#### Scenario: 通知経路が使えない場合
- **WHEN** 変更通知の接続が確立できない
- **THEN** システムは取得のたびに最新の状態を反映し、通知経路の不在を理由に古い内容のまま固定しない

### Requirement: 認可
システムは、認可されていない要求に対してチャネル・ポスト・添付・リアクションを読み書きさせてはならない (MUST NOT)。

#### Scenario: 認可情報の無い要求
- **WHEN** 認可情報を伴わない要求が API へ到達する
- **THEN** システムは要求を拒否し、認可エラーを返す

#### Scenario: 認可情報が失効している
- **WHEN** クライアントが保持する認可情報が失効している
- **THEN** システムは要求を拒否し、クライアントは再認証を促す表示を行う

### Requirement: 楽観的更新と失敗時の巻き戻し
システムは、ユーザー操作の結果を即座に画面へ反映しつつ、サーバー側で失敗した場合には画面表示を元に戻し、失敗をユーザーに通知しなければならない (SHALL)。

#### Scenario: 投稿がサーバーで失敗する
- **WHEN** クライアントがポストをタイムラインへ即時表示した後、サーバーがその作成を拒否する
- **THEN** システムは当該ポストを失敗状態として示し、入力内容を失わせずに再送または破棄をユーザーに選ばせる

#### Scenario: 階層移動がサーバーで失敗する
- **WHEN** クライアントが drag & drop の結果を即時反映した後、サーバーが移動を拒否する
- **THEN** システムはチャネルツリーを取得し直して移動前の状態へ戻し、失敗を通知する

### Requirement: オンライン前提の接続断時の振る舞い
システムはオンライン動作を前提とする。接続できない状態で、システムはデータを変更する操作を成功として扱ってはならない (MUST NOT)。ただし、ユーザーが入力中の内容を失わせてはならない (MUST NOT)。

#### Scenario: 接続断を明示する
- **WHEN** クライアントがバックエンドへ到達できなくなる
- **THEN** システムは接続できていないことを画面上に明示する

#### Scenario: 接続断中の投稿
- **WHEN** 接続できない状態でユーザーがポストを送信する
- **THEN** システムは送信が完了していないことを示し、入力内容を下書きとして保持する

#### Scenario: 古い内容を最新として見せない
- **WHEN** 接続できない状態で画面にデータが残っている
- **THEN** システムはそれが最新であるかのような表示を行わず、接続が回復していない旨を示す

#### Scenario: 接続回復後に最新化する
- **WHEN** 接続が回復する
- **THEN** システムは表示中のチャネルツリーとタイムラインを取得し直して最新の状態にする
