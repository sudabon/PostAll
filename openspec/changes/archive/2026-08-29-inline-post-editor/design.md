## Context

`PostActions` は「鉛筆・ゴミ箱ボタン」と「編集ダイアログ」の両方を 1 コンポーネント（216 行）で抱えている。編集ダイアログは `useOverlayPresence` を使った `<dialog>` で、素の `<textarea>` と添付チェックボックスを持つ。呼び出しは 2 箇所のみ。

- `frontend/src/components/timeline/Timeline.tsx:240`（タイムラインのポスト）
- `frontend/src/components/thread/ThreadPanel.tsx:145`（スレッドの返信）

一方 `Composer`（新規投稿フォーム）は書式ツールバー、コードブロック入力補助、ドラッグ＆ドロップ・貼り付けを含む添付追加、下書きの永続化を持つ。編集フォームはこれらを一切持たない。同じ「本文を書く」操作に 2 つの実装が並存している。

制約として次がある。

- `Timeline` は `ResizeObserver` で高さ変化を検知し、`pinnedToBottom` が真なら最下部へ追従する（`Timeline.tsx:72-83`）。編集フォームは高さが変わるため、この追従を止めないと編集箇所が画面外へ送られる
- 狭幅（iPhone）ではソフトキーボードが画面下部を覆う。`useVisualViewportInset` が `--keyboard-inset` を供給済み
- 削除は `window.confirm` による確認を経る。本変更では触らない

## Goals / Non-Goals

**Goals:**

- 編集フォームを当該ポストの表示位置に開く
- 編集フォームの実体を `Composer` に一本化し、書式ツールバー・コードブロック補助・添付追加を編集でも使えるようにする
- 既存添付をフォームへ引き継ぎ、フォーム上で除去できるようにする
- 編集中はタイムラインの最下部追従を止める
- 狭幅でも編集箇所が可視領域に入る

**Non-Goals:**

- 編集履歴の保持・差分表示（既存 spec が明確に禁止）
- 複数ポストの同時編集
- 編集内容の下書き永続化（意図的に持たない）
- 破棄時の確認ダイアログ。現行のダイアログと同じく取り消しは即座に破棄する
- 削除フローの変更
- API・DB スキーマの変更。`PATCH /v1/posts/{id}` の契約は現行のまま

## Decisions

### 編集状態は `useUi` に置く

`useUi` に `editingPostId: string | null` と `setEditingPost(id)` を追加する。

**理由**: 「同時に 1 件だけ」という要件は、状態を 1 箇所に集約すれば自然に満たせる。また編集トリガー（`PostActions`）と編集フォームの表示位置（`PostBody` の場所）は兄弟関係にあり、共通の親を経由しないと連携できない。

**既存のお手本がある**: チャネル名のリネームが `useUi` の `renaming` と `ChannelTree` のインライン `NameForm` で同じ構造を実装済み。新しいパターンを持ち込まない。

**代替案（不採用）**: `PostRow` のローカル state。トリガーが `PostActions` の内側にあるため props のバケツリレーが必要になり、「同時に 1 件」の保証も各行の外側に別途必要になる。

**永続化しない**: `editingPostId` は `persistedKeys` に加えない。リロードで編集状態が復元されるのは望ましくない。

### `Composer` に編集モードを足す（別コンポーネントを作らない）

`Composer` に任意の編集用 props を追加する。

| props | 役割 |
|---|---|
| `initialBody` | 本文の初期値 |
| `initialAttachments` | 既存添付。保存時に残すものを決める |
| `submitLabel` / `aria-label` | 「送信」ではなく「保存」 |
| `onCancel` | 取り消し。指定時のみ取り消しボタンを出す |
| `persistDraft` | 偽なら下書きを読まない・書かない |
| `autoFocus` | 真ならタッチ端末でもマウント時に本文へフォーカスする |
| `resolveAttachmentUrl` | 既存添付のサムネイル用に署名付き URL を取得する |

**理由**: spec が「新規投稿と同じ規則」で書式ツールバー・コードブロック補助・添付追加が使えることを要求している。別実装にすると仕様が二重管理になり、片方だけ直る事故が起きる。実際に現行のモーダルがその状態にある。

**代替案（不採用）**: `Composer` から入力部分を抽出した共通コンポーネントを作り、新規用と編集用の 2 つのラッパを置く。抽象は綺麗になるが、`Composer` は下書き・アップロード進捗・IME 判定・フェンス判定が絡んでおり、分解のコストと退行リスクが今回の目的に見合わない。編集モードの分岐は数箇所に収まる見込み。

### 既存添付は「アップロード済みの draft」として扱う

`Composer` の内部状態 `DraftFile` は `{ key, file: PickedFile, progress, status, id?, preview? }` を持つ。既存添付はこの型に寄せ、`status: 'ready'` と `id` を設定した項目として初期化する。`file` の実体（バイト列）は持たないため、型を `file` 必須から「表示に必要な名前・サイズ」を持つ形へ広げる。

**理由**: 除去操作・保存時の ID 収集を新規添付と既存添付で分岐させずに済む。保存時は `status === 'ready'` の項目の `id` を集めるだけになる。

**画像のサムネイル**: 既存添付のプレビューには署名付き URL の取得が必要。**取得して表示する**。新規添付は objectURL、既存添付は署名付き URL と経路が違うだけで、利用者から見た添付一覧の見た目が揃う。

取得の口は `Composer` の props（`resolveAttachmentUrl`）として受け取り、呼び出し側が `api.getDownloadUrl` を渡す。`Composer` から `useAuth` を直接呼ぶと、認証プロバイダ無しで描画している既存のフォームのテストが壊れる。アップロードを `uploadFile` として注入している既存の作りに合わせる。取得に失敗してもサムネイルを出さないだけで、添付そのものは扱える。

### 編集モードは常にフォーカスする

常設の `Composer` はタッチ端末でマウント時に自動フォーカスしない（ソフトキーボードがタイムラインを覆い、最初のタップが吸われるため）。編集モードはこの例外とし、開いた時点で本文へフォーカスする。

**理由**: 編集はユーザーが明示的に起動した操作であり、キーボードが出ることは期待どおり。常設フォームの「勝手に出る」問題とは性質が異なる。

### 追従の停止は `Timeline` 側で判定する

`ResizeObserver` のコールバックと `onScroll` で `useUi.getState().editingPostId` を参照し、**かつ当該ポストの行がタイムラインに存在するとき**だけ `pinToBottom` を呼ばず `pinnedToBottom` も書き換えない（`document.getElementById('post-<id>')` の有無で判定する）。

**理由**: `useUi(...)` で購読すると `Timeline` 全体が再描画される。追従の判断は副作用の中でのみ必要なので、`getState()` で十分。

**行の存在まで見る理由**: 編集状態は `useUi` に 1 つしかないので、スレッド内の返信を編集している間も `editingPostId` は非 null になる。id だけで判定すると、返信の編集でタイムラインの追従まで止まる。また対象ポストが取得結果から消えて編集状態だけが残った場合も、追従が戻らなくなる。行の有無を見れば「タイムライン上で編集フォームが開いている」ことだけを判定でき、どちらの取りこぼしも起きない。

**閉じたときの復帰**: `pinnedToBottom` を編集開始時に触らないので、閉じた時点で編集前の値がそのまま残る。明示的な保存・復元は不要。

### 可視化は `scrollIntoView({ block: 'nearest' })`

編集フォームのマウント後に呼ぶ。狭幅ではソフトキーボードの出現で可視領域が変わるため、`visualViewport` の `resize` でももう一度合わせる。`block: 'nearest'` なので既に見えていれば動かない。

## Risks / Trade-offs

**`Composer` の分岐が増えて読みにくくなる** → 編集固有の分岐を「下書きの読み書き」「初期値の投入」「確定ラベル」「取り消しボタン」の 4 点に限定する。それ以上必要になったら共通コンポーネントへの抽出を検討する。

**添付の型を広げることで新規投稿側が壊れる** → 既存添付は `status: 'ready'` で入るため、アップロード経路（進捗・再試行・失敗）は通らない。新規投稿の既存テストで退行を検出する。

**編集中に他者の編集や削除が届き、対象が消える** → 対象ポストが取得結果から消えた場合は編集を終了して本文表示に戻す。保存要求がサーバに拒否される経路は現行と同じ。

**狭幅でキーボードが編集箇所を覆う** → 可視化のスクロールをキーボード出現後（`visualViewport` の `resize`）にも行う。実機（iPhone）での確認を完了条件に含める。

**Escape の誤爆で編集内容が消える** → 現行のモーダルと同じ挙動であり、退行ではない。確認ダイアログは Non-Goals とする。

## Migration Plan

フロントエンドのみの変更で、データ移行はない。1 コミットで投入し、問題があれば revert する。

`PostActions` の `aria-haspopup="dialog"` / `aria-expanded` はダイアログでなくなるため外す。`useOverlayPresence` は絵文字ピッカー・設定・検索で引き続き使うので削除しない。

## Resolved Questions

- **既存の画像添付にサムネイルを出すか** → 出す。編集モードで署名付き URL を取得する。取得の口は `resolveAttachmentUrl` として呼び出し側から注入する（「既存添付は『アップロード済みの draft』として扱う」を参照）
- **編集モードの確定を Shift+Enter でも行えるようにするか** → 行えるようにする。新規投稿の送信と同じ操作に揃え、`Composer` の `onKeyDown` をそのまま流用する。編集固有の分岐を増やさずに済む
- **狭幅で可視化のスクロールをキーボード出現後にも実行する必要があるか** → 実機確認を待たず先に実装する。`PostEditor` がマウント時に加えて `visualViewport` の `resize` でも `scrollIntoView({ block: 'nearest' })` を呼ぶ。`block: 'nearest'` なので既に見えていれば動かず、不要だった場合の副作用がない

## Implementation Notes

**編集状態の後始末を `PostEditor` のアンマウントに置かない**: 「対象ポストが消えたら `editingPostId` を落とす」処理を `PostEditor` のクリーンアップに書くと、StrictMode の「マウント → クリーンアップ → 再マウント」で開いた直後に編集状態が消え、編集フォームが一度も表示されない。後始末は置かず、追従の判定側で行の存在を見ることで、状態が残った場合の実害（追従が戻らない）を消している。
