## Why

ポストの編集を保存すると、サーバーの応答が返るまで編集フォームが開いたまま待たされ、その後にようやくタイムラインへ反映される。投稿・リアクション・チャネル移動はすでに楽観的更新になっているのに、編集だけが「押してから待つ」操作として残っており、体感の遅さと操作の一貫性の欠如を生んでいる。

## What Changes

- 編集の保存を楽観的更新にする。確定操作の直後にサーバーの応答を待たず、編集フォームを閉じ、新しい本文・添付・「編集済み」表示を画面へ反映する。
- サーバー応答が返った時点で、サーバーが返した内容（正規の編集日時・添付など）へ差し替える。差分が無ければ画面は変化しない。
- 保存が失敗した場合は、画面表示を編集前の状態へ巻き戻したうえで、当該ポストの編集フォームを再度開き、ユーザーが入力していた本文と添付を復元し、失敗した旨を編集フォーム内に示す。入力内容を失わせない。
- ただし失敗の時点で別のポストの編集フォームが開いていた場合は、そちらを閉じない。失敗した編集内容は保持しておき、そのポストの編集を再び開いたときに復元して失敗を示す。
- 添付も楽観的更新の対象にする。編集中に追加・除去した添付が、確定操作の直後から正しく表示される。
- 対象はチャネル直下のポストの編集とスレッド内の返信の編集。新規投稿・返信投稿・削除の処理フローは変更しない。

破壊的変更なし。API の要求・応答の形は変わらない。

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `post-timeline`: 「ポストの編集」に、確定操作の直後に反映すること・失敗時に巻き戻して編集を再開させることを追加する。
- `post-threads`: 「スレッド内ポストの編集と削除」に、返信の編集も同じ即時反映と巻き戻しの規則に従うことを明示する。
- `post-composer`: 「入力フォームの編集モード」に、確定操作でフォームが直ちに閉じること・保存失敗時に入力内容を復元した編集フォームが再度開くことを追加する。
- `sync-and-storage`: 「楽観的更新と失敗時の巻き戻し」に、ポストの編集が失敗したときのシナリオを追加する。

## Impact

フロントエンドのみ。バックエンド・API スキーマ・データベースは変更しない。

- `frontend/src/hooks/usePosts.ts` — `edit` mutation を `onMutate` / `onError` / `onSuccess` / `onSettled` 構成へ。
- `frontend/src/lib/reactions.ts` — 内部の React Query キャッシュ走査関数を共有モジュールへ切り出す。
- `frontend/src/state/ui.ts` — 保存に失敗した編集内容を保持する状態を追加する。
- `frontend/src/components/composer/Composer.tsx` — 確定時に添付のメタ情報を呼び出し側へ渡す。初期エラー表示を受け取れるようにする。
- `frontend/src/components/post/PostEditor.tsx` — 失敗した編集内容があればそれを初期値として復元する。
- `frontend/src/components/timeline/Timeline.tsx` / `frontend/src/components/thread/ThreadPanel.tsx` — 保存の呼び出しを「先に閉じてから要求」へ。

既存の楽観的更新（`frontend/src/hooks/useReactions.ts`）と同じ構成を踏襲するため、新しい依存やライブラリの追加は無い。
