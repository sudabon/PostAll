## MODIFIED Requirements

### Requirement: 単一の source of truth
システムは、チャネル・ポスト・添付・リアクションのすべてを Go バックエンドとマネージド PostgreSQL（添付の実体はマネージドオブジェクトストレージ）に保持し、各クライアントはこれを唯一の正とみなさなければならない (SHALL)。

#### Scenario: 各クライアントで同じ内容を見る
- **WHEN** Electron・ブラウザ・iOS が同一のバックエンドへ接続し、同じチャネルを開く
- **THEN** システムはいずれにも同一のチャネル階層とポスト一覧を提供する

#### Scenario: 片方の変更がもう片方に届く
- **WHEN** デスクトップでチャネルの階層を変更する
- **THEN** iOS は次回のデータ取得時に変更後の階層を表示する

#### Scenario: クライアントはデータベースへ直接書き込まない
- **WHEN** クライアントがチャネル・ポスト・リアクション・添付メタデータを変更する
- **THEN** システムはすべての変更を HTTP API 経由でのみ受け付け、クライアントからデータベースへの直接の書き込みを許さない

### Requirement: データモデルの永続化
システムは、チャネルの階層と並び順、ポストの本文と日時、スレッドの親子関係、リアクション、添付のメタデータをマネージド PostgreSQL に永続化しなければならない (SHALL)。スキーマの変更はマイグレーションとして版管理されなければならない (SHALL)。

#### Scenario: 実行インスタンスが入れ替わってもデータが残る
- **WHEN** バックエンドの新しい版がデプロイされ、実行インスタンスが入れ替わる
- **THEN** システムは入れ替え前のチャネル階層・ポスト・スレッド・リアクション・添付をすべて保持している

#### Scenario: マイグレーションを適用する
- **WHEN** 新しいスキーマ版を含むバックエンドをデプロイする
- **THEN** システムはデプロイ工程で未適用のマイグレーションを適用し、適用に失敗した場合は新しい版へ切り替えない

#### Scenario: 参照整合性を保つ
- **WHEN** チャネルまたはポストが削除される
- **THEN** システムは、それに紐づくスレッド・リアクション・添付が不整合な状態で残らないよう一貫した状態を維持する

### Requirement: 変更の反映
システムは、他クライアントによる変更を、表示中のクライアントへ反映する手段を提供しなければならない (SHALL)。変更は単調増加する識別子を持つ変更イベントとして記録されなければならない (SHALL)。クライアントは、リアルタイム通知を受け取った時点で、記録済みの変更イベントを識別子の続きから取得することで表示を最新化しなければならない (SHALL)。

#### Scenario: 表示中チャネルへの新規ポスト
- **WHEN** あるクライアントが表示中のチャネルへ、別のクライアントがポストを追加する
- **THEN** システムは表示中クライアントのタイムラインへ当該ポストを追加する

#### Scenario: 再接続時に取りこぼしを埋める
- **WHEN** クライアントが一時的に接続を失い、その後再接続する
- **THEN** システムは最後に処理した変更イベントの識別子より後の変更をクライアントへ提供し、表示を最新化する

#### Scenario: 通知経路が使えない場合
- **WHEN** 変更通知の接続が確立できない
- **THEN** システムは取得のたびに最新の状態を反映し、通知経路の不在を理由に古い内容のまま固定しない

#### Scenario: 通知に本文を含めない
- **WHEN** リアルタイム通知が配信される
- **THEN** システムは変更があったことを伝えるにとどめ、認可を経ずに読めるチャネル名・ポスト本文・添付の内容を通知の payload へ含めない

#### Scenario: 通知が重複して届く
- **WHEN** 同一の変更に対する通知が複数回届く
- **THEN** システムは重複した反映を行わず、タイムラインへ同じポストを二重に表示しない

#### Scenario: 通知の順序が入れ替わる
- **WHEN** 通知が変更の発生順とは異なる順序で届く
- **THEN** システムは変更イベントの識別子の順序に従って反映し、古い状態で新しい状態を上書きしない

### Requirement: 認可
システムは、認可されていない要求に対してチャネル・ポスト・添付・リアクションを読み書きさせてはならない (MUST NOT)。リアルタイム通知の購読についても認可を要求しなければならない (SHALL)。

#### Scenario: 認可情報の無い要求
- **WHEN** 認可情報を伴わない要求が API へ到達する
- **THEN** システムは要求を拒否し、認可エラーを返す

#### Scenario: 認可情報が失効している
- **WHEN** クライアントが保持する認可情報が失効している
- **THEN** システムは要求を拒否し、クライアントは再認証を促す表示を行う

#### Scenario: 認可されていない通知購読
- **WHEN** 認可情報を伴わない購読要求がリアルタイム通知へ届く
- **THEN** システムは購読を拒否し、通知を配信しない

### Requirement: HTTP API 契約
システムは、チャネル・ポスト・スレッド・リアクション・添付・検索・変更イベントの取得に対する操作を HTTP API として提供しなければならない (SHALL)。API はすべてのクライアントで共通でなければならない (SHALL)。エラーは機械可読なコードと人間可読なメッセージを含む一貫した形式で返さなければならない (SHALL)。API は、応答を長時間にわたって保持し続けるエンドポイントを含んではならない (MUST NOT)。

#### Scenario: チャネル一覧を取得する
- **WHEN** クライアントがチャネル一覧の取得を要求する
- **THEN** システムは階層関係と並び順を復元できる形式でチャネル全体を返す

#### Scenario: ポストを範囲指定で取得する
- **WHEN** クライアントがチャネル ID と位置カーソル、件数を指定してポストの取得を要求する
- **THEN** システムは作成日時の昇順で指定件数のポストと、続きを取得するためのカーソルを返す

#### Scenario: 変更イベントを範囲指定で取得する
- **WHEN** クライアントが直前に処理した変更イベントの識別子と件数を指定して取得を要求する
- **THEN** システムは当該識別子より後の変更イベントを識別子の昇順で返す

#### Scenario: 不正な要求を拒否する
- **WHEN** クライアントが必須項目を欠いた要求、または存在しない ID を指定した要求を送る
- **THEN** システムは対応する HTTP ステータスと、一貫した形式のエラー本文を返す

#### Scenario: 想定外のサーバーエラー
- **WHEN** サーバー内部で想定外のエラーが発生する
- **THEN** システムは内部実装の詳細を漏らさないエラー本文を返し、サーバー側にはエラーの詳細を記録する

#### Scenario: すべての応答が有限時間で完了する
- **WHEN** クライアントがいずれかのエンドポイントへ要求する
- **THEN** システムは有限の時間内に応答を完了させ、接続を保持し続けない
