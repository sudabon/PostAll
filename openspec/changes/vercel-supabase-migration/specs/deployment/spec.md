## ADDED Requirements

### Requirement: マネージドプラットフォームによる構成
システムは、フロントエンドの静的アセットと API サーバをマネージドホスティングへ、データベース・認証・オブジェクトストレージ・リアルタイム配信をマネージド BaaS へ配置しなければならない (SHALL)。運用者がサーバー OS、リバースプロキシ、証明書、データベースプロセスを直接管理してはならない (MUST NOT)。

#### Scenario: 単一の定義から構成を手動デプロイする
- **WHEN** 運用者が GitHub Actions のデプロイワークフローを手動実行する
- **THEN** システムは選択された Git ref とリポジトリ内のデプロイ定義に従って静的アセットと API サーバをビルドし、公開可能な状態にする

#### Scenario: Git への変更だけではデプロイしない
- **WHEN** いずれかのブランチへ commit が push される
- **THEN** システムはVercelデプロイを自動で開始しない

#### Scenario: 設定値を環境変数で与える
- **WHEN** 運用者が接続先やシークレットを環境変数で与える
- **THEN** システムは成果物を再ビルドすることなく設定を反映し、シークレットを成果物へ埋め込まない

#### Scenario: デプロイに失敗する
- **WHEN** ビルドまたはデプロイが失敗する
- **THEN** システムは稼働中の版を切り替えず、失敗を運用者が検知できる形で残す

### Requirement: 単一オリジンでの配信と振り分け
システムは、フロントエンドと API を同一のオリジンで公開し、パスによって振り分けなければならない (SHALL)。API サーバとデータベースを、この公開経路以外から直接到達できる状態にしてはならない (MUST NOT)。

#### Scenario: API へ振り分ける
- **WHEN** クライアントが API のパスへ要求する
- **THEN** システムは当該要求を API サーバへ転送し、応答を返す

#### Scenario: PWA を配信する
- **WHEN** ブラウザがアプリのルート URL へ要求する
- **THEN** システムは PWA の静的アセットを配信する

#### Scenario: SPA のルーティングを壊さない
- **WHEN** ブラウザが PWA の任意のパスへ直接アクセスする
- **THEN** システムはアプリシェルを返し、404 を返さない

#### Scenario: API のパスをアプリシェルへ落とさない
- **WHEN** クライアントが存在しない API のパスへ要求する
- **THEN** システムはアプリシェルではなく API のエラー応答を返す

#### Scenario: 静的アセットのキャッシュ指示
- **WHEN** ブラウザが内容ハッシュ付きの静的アセット、Service Worker スクリプト、または web app manifest を取得する
- **THEN** システムは、内容ハッシュ付きアセットには長期かつ不変であることを示すキャッシュ指示を、Service Worker スクリプトと manifest には再検証を求めるキャッシュ指示を返す

#### Scenario: クライアントが別オリジンにならない
- **WHEN** PWA が API を呼び出す
- **THEN** システムは同一オリジンの相対パスで到達させ、クライアントがオリジン間要求を行わずに済むようにする

### Requirement: サーバーレス実行モデルへの適合
システムは、要求の処理が完了した後もプロセスが生存し続けることを前提としてはならない (MUST NOT)。API サーバは、要求の処理外で動作する常駐処理や、インスタンス内メモリに保持した状態へ依存してはならない (MUST NOT)。

#### Scenario: インスタンスが増減する
- **WHEN** 同一の要求が異なるインスタンスで処理される
- **THEN** システムは同一の結果を返し、特定のインスタンスに蓄積された状態へ依存しない

#### Scenario: 応答後の処理を当てにしない
- **WHEN** 要求の処理中に、応答の返却後も継続する必要のある作業が発生する
- **THEN** システムは当該作業を永続化された状態として記録し、後続の実行が引き継げるようにする

#### Scenario: 長時間の接続保持を要求しない
- **WHEN** クライアントが変更通知を受け取ろうとする
- **THEN** システムは API サーバとの接続を長時間保持させることなく通知を成立させる

### Requirement: 定期実行タスク
システムは、時間を契機に実行される保守処理を、スケジューラからの起動によって実行しなければならない (SHALL)。当該起動経路は、権限のない要求から実行されてはならない (MUST NOT)。

#### Scenario: 未確定の添付を回収する
- **WHEN** スケジュールされた時刻が到来する
- **THEN** システムは回収対象の添付を処理し、処理件数と失敗を記録する

#### Scenario: 期限切れの変更イベントを整理する
- **WHEN** スケジュールされた時刻が到来する
- **THEN** システムは30日を超えた変更イベントを整理し、処理件数と失敗を記録する

#### Scenario: 権限のない起動要求
- **WHEN** スケジューラ以外からタスクの起動経路へ要求が届く
- **THEN** システムは要求を拒否し、タスクを実行しない

#### Scenario: 実行が重なる
- **WHEN** 前回の実行が完了しないうちに次の起動が届く
- **THEN** システムは同一の対象を二重に処理せず、不整合な状態を残さない

### Requirement: データベース接続の管理
システムは、データベースへの接続をプーラー経由で確立し、実行インスタンスの増加によってデータベースの接続上限を枯渇させてはならない (MUST NOT)。

#### Scenario: 同時実行数が増える
- **WHEN** 多数の要求が同時に処理される
- **THEN** システムはデータベースの接続上限を超えず、接続の確立に失敗した要求を無言で成功として扱わない

#### Scenario: プーラーの制約に適合する
- **WHEN** API サーバがデータベースへ問い合わせる
- **THEN** システムはプーラーが接続を要求ごとに割り当て直す前提と矛盾しない方法で問い合わせを実行する

#### Scenario: セッションに紐づく機能へ依存しない
- **WHEN** システムがデータベースの機能を利用する
- **THEN** システムは、同一の接続が保持され続けることを前提とする機能へ依存しない

### Requirement: 全文検索索引が利用できる PostgreSQL
システムは、日本語を含む本文の部分一致検索を索引によって成立させられる PostgreSQL を利用しなければならない (SHALL)。当該索引の実装は、マネージド PostgreSQL が提供する拡張の範囲で選ばなければならない (SHALL)。

#### Scenario: 拡張を有効化する
- **WHEN** マイグレーションが全文検索用の拡張の作成を実行する
- **THEN** システムはエラーなく拡張を有効化し、本文に対する索引を作成できる状態になる

#### Scenario: 持ち込み拡張に依存しない
- **WHEN** システムがマネージド PostgreSQL 上で起動する
- **THEN** システムは、プラットフォームが提供しない拡張の導入を必要としない

### Requirement: データのエクスポート
システムは、データベースの内容を定期的にエクスポートし、プラットフォームの外に保持しなければならない (SHALL)。エクスポートの取得はスケジューラからの起動によって自動で行われなければならず、運用者の手動操作に依存してはならない (MUST NOT)。

#### Scenario: 定期的にエクスポートを取得する
- **WHEN** スケジュールされた時刻が到来する
- **THEN** システムはデータベースの内容をエクスポートし、プラットフォームの外の保管先へ保存する

#### Scenario: エクスポートに失敗する
- **WHEN** エクスポートの取得が失敗する
- **THEN** システムは失敗を運用者が検知できる形で残し、直前に成功したエクスポートを破棄しない

#### Scenario: エクスポートから復旧する
- **WHEN** 運用者が取得済みのエクスポートから新しいデータベースを構築する
- **THEN** システムはチャネル階層・ポスト・スレッド・リアクション・添付メタデータを復元し、稼働可能な状態になる

### Requirement: 無操作による停止の回避
システムは、一定期間アクセスが無いことを理由にプラットフォームがプロジェクトを停止させる状態へ陥ってはならない (MUST NOT)。

#### Scenario: 利用が途切れる
- **WHEN** 利用者による操作が一定期間行われない
- **THEN** システムは定期実行によってデータベースへのアクセスを発生させ、プラットフォームによる停止の条件を満たさない状態を保つ

#### Scenario: 停止が発生した場合に検知できる
- **WHEN** それでもプラットフォームがプロジェクトを停止させる
- **THEN** システムは応答できないことを運用者が検知できる形で残し、利用者には接続できない旨を示す

## MODIFIED Requirements

### Requirement: HTTPS の強制
システムは、すべての公開エンドポイントを HTTPS で提供しなければならない (SHALL)。HTTP での要求は HTTPS へリダイレクトされなければならない (SHALL)。TLS 証明書の取得と更新はホスティングプラットフォームの責務とし、運用者の操作を要してはならない (MUST NOT)。

#### Scenario: HTTP でアクセスされる
- **WHEN** クライアントが HTTP でアクセスする
- **THEN** システムは同一パスの HTTPS へリダイレクトする

#### Scenario: 証明書が期限に近づく
- **WHEN** TLS 証明書の有効期限が更新の閾値に達する
- **THEN** プラットフォームが証明書を更新し、運用者の操作もサービスの停止も生じない

#### Scenario: 独自ドメインで応答する
- **WHEN** 運用者が独自ドメインを割り当てる
- **THEN** システムは当該ドメインに対する証明書を備えた状態で HTTPS 応答を返す

### Requirement: データの永続化
システムは、チャネル・ポスト・スレッド・リアクション・添付のメタデータをマネージド PostgreSQL に、添付と絵文字の実体をマネージドオブジェクトストレージに永続化しなければならない (SHALL)。これらは API サーバの実行インスタンスのライフサイクルから独立していなければならない (SHALL)。

#### Scenario: API サーバが作り直される
- **WHEN** 新しい版がデプロイされ、実行インスタンスが入れ替わる
- **THEN** システムは既存のチャネル・ポスト・添付メタデータ・添付実体を保持したまま応答を継続する

#### Scenario: バックアップから復旧できる
- **WHEN** 運用者がデータベースの復旧を必要とする
- **THEN** システムは定期的に取得されたエクスポートから復旧でき、直近のエクスポート以降の変更のみが失われる範囲に損失をとどめる

### Requirement: マイグレーションの適用
システムは、スキーマのマイグレーションが未適用の状態で新しい版へ切り替わってはならない (MUST NOT)。マイグレーションは要求の処理経路ではなく、デプロイとは独立した手動 GitHub Actions で適用されなければならない (SHALL)。デプロイはマイグレーションを適用してはならない (MUST NOT)。

#### Scenario: 新しいスキーマ版を手動で適用する
- **WHEN** 運用者がマイグレーションワークフローを手動実行する
- **THEN** システムは選択された Git ref の未適用マイグレーションを適用し、成功後に絵文字カタログを同期する

#### Scenario: マイグレーションとデプロイを分ける
- **WHEN** マイグレーションワークフローが完了する
- **THEN** システムはデプロイを自動起動せず、運用者による別ワークフローの手動実行を待つ

#### Scenario: 要求の処理中にマイグレーションを走らせない
- **WHEN** API サーバのインスタンスが新たに起動する
- **THEN** システムはマイグレーションを実行せず、要求の応答時間へ影響を与えない

#### Scenario: 未適用のままデプロイしようとする
- **WHEN** 未適用のマイグレーションがある状態でデプロイワークフローを手動実行する
- **THEN** システムはデータベースを変更せずにデプロイを失敗させ、マイグレーションワークフローの先行実行が必要である旨を記録する

### Requirement: ヘルスチェック
システムは、稼働状態を判定できるヘルスチェックを提供しなければならない (SHALL)。

#### Scenario: API サーバの稼働を確認する
- **WHEN** ヘルスチェックが API サーバへ問い合わせる
- **THEN** システムは依存する PostgreSQL への接続可否を含めた稼働状態を返す

#### Scenario: 依存先が落ちている
- **WHEN** PostgreSQL へ接続できない状態でヘルスチェックが実行される
- **THEN** システムは不健全であることを示す応答を返す

#### Scenario: ヘルスチェックは認可を要さない
- **WHEN** 認可情報を伴わない要求がヘルスチェックへ届く
- **THEN** システムは稼働状態を返し、内部構成の詳細を漏らさない

## REMOVED Requirements

### Requirement: コンテナによる構成
**Reason**: Nginx / Certbot / API サーバ / PostgreSQL を自前のコンテナとして配備する前提を廃止し、マネージドホスティングとマネージド BaaS へ移行するため。
**Migration**: 「マネージドプラットフォームによる構成」「サーバーレス実行モデルへの適合」「データベース接続の管理」の各要件が代替する。`infra/docker-compose.yml` と関連定義は削除する。

### Requirement: リバースプロキシによる振り分け
**Reason**: Nginx を TLS 終端かつ唯一の公開エンドポイントとする構成を廃止し、ホスティングプラットフォームのルーティングへ委ねるため。SSE 接続の中継設定という要件も、変更通知の方式変更により不要になる。
**Migration**: 「単一オリジンでの配信と振り分け」が代替する。アップロード要求のサイズ制限は、署名付き URL によるクライアント直接アップロードにより API サーバを経由しないため、`attachments` の要件で担保する。

### Requirement: 証明書の取得と自動更新
**Reason**: Certbot による証明書の取得・更新・反映を自前で運用する前提を廃止するため。
**Migration**: 「HTTPS の強制」の要件がプラットフォーム責務として証明書の取得と更新を含む。`infra/certbot/` と `infra/certs/` は削除する。

### Requirement: `pg_bigm` を含む PostgreSQL
**Reason**: マネージド PostgreSQL は `pg_bigm` を提供せず、拡張を持ち込むこともできないため。
**Migration**: 「全文検索索引が利用できる PostgreSQL」が代替する。索引実装の具体は `full-text-search` の要件で規定する。`infra/postgres/Dockerfile` は削除する。
